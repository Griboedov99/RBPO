# Модель угроз (S03)

**Команда:** 247_number_one
**Продукт:** RepairTrack — учёт техники на ремонте (см. [PROJECT.md](PROJECT.md))
**Статус:** предварительная модель для S03; дорабатывается к S04 (связи с `D-*` и будущими проверками — S04).

Форма — по шаблону курса `threat-model.md`; угрозы связаны с требованиями [security-requirements-repairtrack.md](security-requirements-repairtrack.md).

## Модель продукта

```text
клиент-владелец (браузер / HTTP) ─┐
                                  ▼
клиенты сотрудников (Swagger/curl) ─▶ API-сервер (FastAPI) ─▶ хранилище (SQLite/SQLAlchemy)
```

Компоненты, потоки и точки входа — из паспорта `PROJECT.md` (разделы 6, 8, 9):

- **API-сервер (FastAPI):** предметная логика заказов, проверка подлинности, ролей и допустимых переходов статусов; единственный компонент, принимающий решения.
- **Хранилище (SQLite через SQLAlchemy):** заказы, диагностика, работы, журнал статусов, учётные записи сотрудников.
- **Клиенты сотрудников (Swagger UI / HTTP-клиент):** действуют от имени приёмщика, инженера или руководителя.
- **Клиент владельца:** анонимный вызов публичного эндпоинта статуса по номеру квитанции и коду.

**Точки входа:** создать заказ; найти заказ; назначить инженера; добавить диагностику и работы; сменить статус; выдать устройство; управлять учётными записями; публичный статус по номеру квитанции и коду.

**Что уже существует:**

Документная основа: паспорт `PROJECT.md`, требования `SR-01`–`SR-09` с критериями приёмки, настоящая модель. Запускаемая техническая основа пока не реализована (планируется к EK1).

**Что пока планируется:**

Серверное приложение FastAPI с хранилищем SQLite, эндпоинты по точкам входа выше, вход сотрудников по учётным данным (механизм — уровень S04, `D-*`).

**Существенные допущения:**

- подлинность сотрудника устанавливается при входящем по учётным данным (SR-01); способ не проектируется здесь;
- хранилище и сервер находятся на одной машине запуска, внешних сервисов нет;
- анонимный клиент взаимодействует только с публичным статусом;
- роль сотрудника сервер определяет из своего контекста подлинности, а не из параметров запроса.

## Границы доверия

| Граница | Что пересекает | Почему требуется проверка |
| --- | --- | --- |
| Клиент → API-сервер | Тело JSON, параметры пути и запроса, идентификаторы заказов, номера квитанций и коды, данные входа | Клиентская сторона недоверенна: корректный синтаксис не означает допустимость действия. Сервер самостоятельно проверяет подлинность, роль, права на объект и допустимость состояния |
| API-сервер → хранилище | Чтение и изменение состояния заказов, журнала и учётных записей | Внутренняя граница той же машины доверия; решения о записи принимает только сервер после проверки полномочий |

## Значимые объекты и свойства

Перечень и последствия нарушения — раздел 5 `PROJECT.md` (заказы, диагностика и работы, статус и журнал, учётные записи). Существенные для модели свойства:

- разграничение действий по ролям и назначению (SR-01, SR-02, SR-03);
- выдача и закрытие только с верным кодом и от верной роли (SR-04);
- неизменяемость фактов приёма/выдачи и закрытого заказа, допустимые переходы и неизменяемый журнал (SR-05, SR-06, SR-07);
- конфиденциальность публичного статуса и учётных данных (SR-08, SR-09).

## Угрозы

| ID | Сценарий угрозы | Что нарушается | Граница / точка входа | Связанные SR | Приоритет и обоснование |
| --- | --- | --- | --- | --- | --- |
| T-01 | Инженер подставляет в запрос идентификатор заказа, назначенного другому инженеру или ещё никому, и через прямой запрос (либо список/поиск) читает/изменяет его диагностику, работы и стоимость | Конфиденциальность и целостность данных чужих заказов; необоснованная стоимость | Граница клиент → сервер; вход: ID заказа в запросе | SR-02, SR-03 | высокий; реалистичен прямой вызов API, последствия — правка чужих записей и стоимости → приоритет |
| T-02 | Сотрудник или клиент без входа напрямую вызывает операцию, разрешённую другой роли: приёмщик добавляет диагностику, инженер создаёт заказ или назначает инженера, аноним вызывает внутренние операции | Полномочия и роли; действие вне полномочий | Граница клиент → сервер; любой внутренний эндпоинт | SR-02 | высокий; основное разграничение функций, последствия — правка чужих данных и выдача → приоритет |
| T-03 | Злоумышленник подбирает или перехватывает код получения и предъявляет чужой код при выдаче, либо приёмщик выдаёт без сверки; при любом несовпадении сервер отвечает единым отказом, не раскрывая, какой параметр неверен | Целостность выдачи, утрата устройства, спор с владельцем | Точка входа «выдать устройство»; вход: номер квитанции и код | SR-04 | высокий; последствия — утрата устройства, невозможность закрыть заказ штатно → приоритет |
| T-04 | Анонимный клиент перебирает номера квитанций и коды публичного статуса либо запрашивает статус по одному номеру, пытаясь узнать данные или факт существования чужого заказа | Конфиденциальность: раскрытие данных и существования чужого заказа | Публичный эндпоинт статуса; вход: квитанция и код, серия запросов | SR-08 | средний; перебор реалистичен, но клиенту доступен только минимум данных при едином отказе |
| T-05 | Сотрудник или запрос через API изменяет/удаляет факты приёма или выдачи после фиксации: комплектность, состояние, запись о выдаче, поля или весь закрытый заказ | Целостность зафиксированных фактов и доказательность; невозможность установить ответственность, спор о пропаже/повреждении | Граница клиент → сервер; вход: JSON правки данных приёма/выдачи | SR-07 | высокий; подмена комплектности или выдачи — утрата учёта и доверия → приоритет |
| T-06 | Сотрудник переводит заказ недопустимым путём (пропуск шагов, повторный переход, смена статуса чужого заказа) либо изменяет/удаляет записи журнала статусов | Согласованность состояния; невозможность установить ответственного | Точка входа «сменить статус»; вход: новый статус, ID заказа | SR-05, SR-06 | средний; ложные статусы и утрата аудита, но влияет на состояние внутри серверного контура |
| T-07 | Злоумышленник получает учётные данные сотрудника (подбор, компрометация) и входит от его имени, получая полномочия приёмщика/инженера/руководителя,  включая выдачу и управление учётными записями; при неуспешном входе сервер не раскрывает, существует ли учётная запись | Подлинность и полномочия; действия от имени сотрудника | Граница клиент → сервер; вход: логин и пароль | SR-01, SR-09 | высокий; последствия — действия с критичными полномочиями при раскрытии учётных данных → приоритет |
| T-08 | Сотрудник или клиент пподаёт некорректный или злонамеренный ввод (отрицательная сумма работы, код статуса вне допустимого перехода, данные приёма на закрытом заказе), из-за которого сервер некорректно изменяет состояние | Целостность состояния; изменение без полномочий | Граница клиент → сервер; любой вход | SR-02, SR-05, SR-07 | средний; защитный смысл — «некорректный запрос не изменяет состояние», реалистичен через точки ввода данных |

## Приоритетный набор

Приоритетные угрозы — **T-01, T-02, T-03, T-05, T-07**.

Обоснование выбора: все они реализуемы через недоверенные точки входа API (прямой вызов, подстановка идентификаторов и кодов, данные входа) и ведут к последствиям, признанным значимыми в паспорте: утрата устройства, действие от имени сотрудника, правка чужих и закрытых данных. Каждая угроза связана с приоритетным SR и будет влиять на проектные решения `D-*` на S04. Остальные угрозы (T-04, T-06, T-08) вторичны: их решения могут вытекать из выбранных (единые отказы, неизменяемый журнал, серверная валидация).
